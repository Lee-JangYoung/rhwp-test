# 문서 유형 프로필과 양식 등록

결정: [ADR-0006](../adr/0006-template-registration-and-doctype-profile.md), [ADR-0007](../adr/0007-llm-by-host-agent-conversion-llm-free.md). 이 문서의 스키마와 파일 형식은 **가설**이며 스파이크(S-01, S-03, S-10, R-01~R-03) 후 확정한다.

## 개념
**프로필**은 문서 유형 하나(유스케이스·클래스·DB 명세서 등)의 변환 정의다. 샘플 양식(HWP/HWPX)을 **등록**해 만들고, 이후 변환은 프로필만 보고 수행한다. 프로필은 파일 묶음이라 git으로 관리한다.

```
templates/<유형>/
├── 양식.hwpx          # 등록한 양식 원본 (개인정보 제거본)
├── template.md        # AI에게 줄 md 골격
├── schema.json        # 규약: 헤딩·표 열 이름/순서·필수·반복 단위·타입
├── profile.yaml       # md 요소 → 양식 스타일/필드 매핑 (구 style-map)
└── prompt.md          # AI 작성 지침 + 예시
```

## 등록 흐름 (양식당 1회)
```
샘플 HWP → ① 분석(프로그램) → ② 해석·초안(LLM) → ③ 검토·승인(사람) → 프로필 저장
```

## 변환 흐름 (문서마다)
```
template.md → ④ AI가 md 작성 → ⑤ 규약 검증 → ⑥ 변환 → ⑦ 검증 → HWP/HWPX
                      ▲            │ 위반 메시지(자기 교정)
                      └────────────┘
```

## 프로그램 vs LLM 분담

원칙: **LLM은 의미 해석에만, 변환·검증은 결정적(프로그램)으로.** LLM 결과는 JSON 스키마로 검증한 뒤 파일로 고정한다. 변환 시점에는 LLM을 쓰지 않는다.

| 단계 | 작업 | 담당 |
|---|---|---|
| ① | 표 행·열·병합, 머리행 텍스트, 누름틀·책갈피, 스타일 이름, 개요, 쪽 설정 추출 | 프로그램 |
| ① | 반복 블록 **후보** 탐지(같은 모양 블록) | 프로그램(휴리스틱) |
| ② | 표의 의미 해석, 항목명 정규화·키 명명, 필수/선택·타입 추정 | LLM |
| ② | 작성 지침(`prompt.md`)과 예시 값 작성 | LLM |
| ② | `template.md`·`schema.json`·`profile.yaml` 초안 조립 | 프로그램(LLM 제안을 스키마로 검증) |
| ③ | 반복 단위·필수 여부 확정, 프로필 커밋 | 사람 |
| ④ | md 본문 작성 | LLM(사용자 측) |
| ⑤ | 스키마 검증, 위반 메시지 생성 | 프로그램 |
| ⑥ | md 파싱 → 매핑 → rhwp 편집 → 저장 | 프로그램 |
| ⑦ | 재로드, 쪽수·텍스트·구조 비교, 손실 확인, SVG 미리보기 | 프로그램 |
| 최종 | 한컴오피스에서 열림·충실도 확인 | 사람 |

## 대상 문서 유형 (SI 산출물)
셋 다 "항목 1건 = 블록이 반복되는 표 중심 문서"다.

| 유형 | 블록 구성 (예시, 실제 양식에서 도출) |
|---|---|
| 유스케이스 명세서 | 헤더 정보(ID, 액터, 사전/사후조건) + 기본/대안/예외 흐름(번호 목록) + 다이어그램 |
| 클래스 명세서 | 헤더 정보 + 속성표 + 메서드표 + 관계 |
| DB 명세서(테이블) | 헤더 정보 + 컬럼 정의표 + 인덱스/제약표 + ERD |

md 골격 예 (유스케이스, 확정 아님)

````markdown
---
type: usecase
title: 회원 유스케이스 명세서
version: 1.0
---

## UC-001 로그인

| 항목 | 내용 |
|---|---|
| 액터 | 일반 회원 |
| 사전조건 | 회원가입 완료 |

**기본 흐름**
1. 사용자가 ID/비밀번호를 입력한다.
````

## 입력 규약 공통 규칙
1. 문서 1개 = 유형 1개, front-matter에 `type`을 둔다.
2. 항목 1건 = H2 하나(`## UC-001 로그인`).
3. 헤더 정보는 2열 표(`항목|내용`), 목록형 표는 열 이름·순서 고정.
4. 흐름은 번호 목록, 다이어그램은 ```` ```mermaid ````.
5. 병합 셀·원시 HTML 금지(병합은 양식 쪽에서 처리).
6. 위반은 줄 번호·기대 값을 포함한 메시지로 반환한다.

## profile.yaml 예 (가설)

```yaml
version: 1
type: usecase
template: 양식.hwpx
contentStart: 본문시작            # 본문 삽입 위치(책갈피), 없으면 문서 끝
repeat: { unit: 유스케이스 }       # 반복 블록 처리 방식은 R-02로 확정
styles: { heading1: 개요 1, heading2: 개요 2, body: 바탕글, caption: 캡션 }
fields: { title: 제목, version: 버전, author: 작성자, date: 작성일 }
output: { defaultFormat: hwpx }
```

- `styles` 값은 양식에 존재하는 스타일 이름이어야 한다. 시작 시 `getStyleList()`와 대조하고, 없으면 경고 후 `body`로 대체한다(`--strict`는 중단).
- 개인정보가 있는 양식은 커밋하지 않는다.

## 미결: 생성형 vs 채움형 [검증 필요 R-02]

| 방식 | 설명 | 위험 |
|---|---|---|
| 생성형 | md 표를 코드로 새로 만들고 스타일·표 속성을 입힘 | 양식의 병합·테두리와 달라질 수 있음 |
| 채움형 | 양식의 표에 값을 채우고 반복 블록은 복제 | rhwp에서 블록 복제 가능 여부 불확실 |
