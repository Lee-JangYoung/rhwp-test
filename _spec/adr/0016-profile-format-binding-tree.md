# ADR-0016: 프로필 형식은 바인딩 트리, kind는 등록부로 확장한다

- 상태: 채택 (I-2, 합성 양식 1종에서 검증). [ADR-0006](0006-template-registration-and-doctype-profile.md)의 프로필 형식을 구체화한다.
- 날짜: 2026-10-15

## 배경
PoC는 유스케이스 한 종류의 매핑을 코드에 박아 두었다. 실제 SI 양식은 항목마다 표가 반복되는 경우, 헤더 표와 목록 표가 함께 반복되는 경우(클래스·DB 명세서), 문서 전체가 하나의 목록 표인 경우 등 패턴이 다양하다. 개발자 요구: 다양한 패턴을 수용하고, LLM이 프로필을 쓰고 사람이 일부를 고치며, 환각을 줄일 것.

## 결정
- 프로필은 **바인딩의 목록**(양식 위치 × md 데이터 × 동작 `kind`)이며 `repeat`로 **중첩**할 수 있다(깊이 제한 없음). md는 고정 구조가 아니라 **컬렉션·슬롯** 선언으로 읽는다.
- **kind는 코드 등록부(`kinds.ts`)에서만 추가**한다. 스키마·가이드·점검이 이 등록부에서 생성되어 구현과 어긋나지 않는다. 새 패턴은 새 kind(또는 위치 지정)를 등록해 추가하며 형식 `version`은 올리지 않는다.
- **검증된 것만 켠다**: 정의만 된 kind(`rows`, `paragraphs`, `remove`, `text`)는 스키마가 구조를 검사하지만 `checkProfile`이 거부한다. 검증 후 활성화한다.
- 알 수 없는 키·kind는 오류, 임의 코드·표현식 없음(조건은 `empty`·`exists`만). 기본값을 두어 짧게 쓴다.
- LLM 친화: `analyzeTemplate`(사실), `describeKinds`(검증된 어휘), `getProfileGuide`(생성된 가이드), `parseProfile`·`checkProfile`(줄 번호·후보가 있는 구조화 오류).
- 도구는 프로필 파일을 다시 쓰지 않는다(사람의 수정·주석 보존).

## 대안
| 대안 | 단점 |
|---|---|
| 표·행 2층 고정(`unit`+`fill`) | 블록 반복·중첩·목록 문서 등 새 패턴마다 형식 변경 |
| 임의 스크립트·표현식 | 검증·점검 불가, LLM 환각·보안 위험 |
| 프로필에서 스키마 생성 | md 규약은 별도 JSON Schema 파일을 참조하는 쪽이 도구·오류 체계가 이미 있음 |

## 결과
- 키 레퍼런스는 [profile-reference.md](../04-conversion/profile-reference.md)(자동 생성), JSON Schema는 `packages/core/schema/profile.schema.json`. 저장된 파일과 생성 결과의 일치를 시험이 지킨다.
- 형식은 합성 유스케이스 양식 1종에서 검증됐다. 실제 양식에서 모자라면 kind·위치 지정을 추가한다(I-5·I-6).
